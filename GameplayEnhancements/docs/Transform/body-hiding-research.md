# Cheaters hide Valheim bodies by lying about height

**The one mechanism found that hides a player's human body from fully vanilla viewers is a position lie told by the cheater's own client: while the client sends its player object to the server, it writes a height of 10000 into that object, so the server and every viewer place the body 10 km up.** It is the `ghost_invisibility` setting of Server Devcommands. It is a pure client-side Harmony patch on the cheater's machine, with no server component, no RPC and no ZDO key that viewers must understand ([GhostFeatures.cs](https://github.com/JereKuusela/valheim-dev/blob/main/ServerDevcommands/Features/GhostFeatures.cs), [README](https://github.com/JereKuusela/valheim-dev/blob/main/README.md)). Nothing else the notes cover hides the base body for vanilla viewers. Scale is not synced for the Player prefab, vanilla ghost mode is a local flag, and equipment hashes can add items but cannot remove the base body. Every public "looks different" mod (Fenrir Curse, Races of Valheim, BoneMod, ValheimVRM, Player_Scaling, GhostWalk) requires the mod on each viewer. Paired with a separately spawned, networked creature that follows the real position, the result for a vanilla viewer is a creature with no human next to it. That combination was not tested end to end. The trick leaks through shout and ping positions, the player-list entry, the creature's behaviour and the player object's own data. The server can see the contradiction between the object's height and the peer's reference position, so a host-side plugin can detect and clamp it. The conclusions rest on source reading, not on a two-client live test. No public admin case report of this was found.

## Valheim trusts the sender, so one lie reaches vanilla viewers

The game is client-authoritative: the owner's client decides where its objects are, and the server stores and relays the data. In the intake path the owner's IL reading covers (`ZDOMan.RPC_ZDOData`), the server checks only that the sender is a known connection and compares revision numbers. It does not check position, prefab, rate or ownership plausibility (the owner's IL reading of Valheim 1.0.20, in the earlier research; a third-party decompile of an older build shows the same position handling, `InternalSetPosition` with no plausibility check). A hosting guide and the author of AzuAntiCheat say the same thing: the game is client authoritative, and not everything the client does can be checked ([AzuAntiCheat](https://thunderstore.io/c/valheim/p/Azumatt/AzuAntiCheat/)). Three channels reach vanilla viewers, because their own code already processes them: object data (a spawned prefab, the player's own object with position and equipment hashes), routed messages that every client executes, and world state. A model that exists only in the cheater's own memory is never sent, so viewers see the human.

Server Devcommands exploits the first channel with almost no code. A prefix on `ZDOMan.SendZDOs` saves the local player's real height and writes 10000 into the player object's position, and a postfix restores the real value after the call. The lie therefore exists only while the send runs and never enters the cheater's own game state ([GhostFeatures.cs](https://github.com/JereKuusela/valheim-dev/blob/main/ServerDevcommands/Features/GhostFeatures.cs)). A second patch on `ZNet.SendPeriodicData` clears the "public reference position" flag while the periodic data goes out. The server builds the map player list from that flag, so the map pin disappears too (vanilla `ZNet` code in the [third-party decompile](https://github.com/VFlov/ValheimMods/blob/main/PrettyPotion/assembly_valheim/ZNet.cs)). The real reference position is still sent, because the server needs it to load zones.

Height 10000 works because zones are computed from x and z only (`ZoneSystem.GetZone`). The object stays in the same sector, so it is still sent to the same nearby viewers. Viewers instantiate remote players at the position in the object, so the body is created 10 km above the world. The vanilla enemy nameplate appears only within 10 m of the local player, so no name shows ([EnemyHud](https://github.com/VFlov/ValheimMods/blob/main/PrettyPotion/assembly_valheim/EnemyHud.cs), [ZoneSystem](https://github.com/VFlov/ValheimMods/blob/main/PrettyPotion/assembly_valheim/ZoneSystem.cs)). The repo README says to install the mod "on the admin client and optionally on the server", and `ghost_invisibility` is not on its list of features needing the server. The code has no server-side branch ([README](https://github.com/JereKuusela/valheim-dev/blob/main/README.md)).

Three caveats limit this finding. The README and the code are the evidence; no release note states "works with vanilla viewers", and no live test with a second client was done. The vanilla code was read from an older third-party decompile (network version 34); only identifier names were confirmed in the installed 1.0.20 assembly, and the InvisibilityPotion author's own notes from a 1.0-era decompile describe the same structure. The exact on-screen behaviour of a non-owner player at that height (physics, gravity handling in `ZSyncTransform`) is unverified. The admin gate of the mod is also client-side. It consults a permission manager that defaults to admin-only, but the mod's own documentation says players can always uninstall it. The server never checks it, so a modified client does not need admin rights to send a spoofed position. The notes did not read the permission manager for non-admins on a vanilla server ([permissions.md](https://github.com/JereKuusela/valheim-dev/blob/main/permissions.md)).

## Which routes need a mod on the viewer and which do not

| Route | Viewer mod needed? | Evidence |
|---|---|---|
| Height lie in `SendZDOs` on the cheater's client (Server Devcommands `ghost_invisibility`) | No | Client-side patch, no RPC or ZDO key for viewers ([GhostFeatures.cs](https://github.com/JereKuusela/valheim-dev/blob/main/ServerDevcommands/Features/GhostFeatures.cs)) |
| The same lie done on the server (InvisibilityPotion tier III) | Technique: no. The mod itself: yes, it is set to "EveryoneMustHaveMod" | [PlayerHidePatches.cs](https://github.com/saiko-psych/InvisibilityPotion/blob/main/InvisibilityPotion/Patches/PlayerHidePatches.cs), [wiki 05](https://github.com/saiko-psych/InvisibilityPotion/blob/main/docs/wiki/05-Multiplayer-and-Server.md) |
| Spawning a vanilla creature prefab as a networked object | No | The owner's earlier IL reading: viewers instantiate by prefab hash |
| Putting any vanilla ObjectDB item on the player's equipment slots | No | The owner's IL: `AttachItem` uses `ObjectDB.GetItemPrefab(hash)` |
| Resizing or reshaping the player (Player_Scaling, BoneMod) | Yes | Player_Scaling sets `m_syncInitialScale` on the Player prefab on every client ([source](https://raw.githubusercontent.com/JereKuusela/valheim-player_scaling/main/PlayerScaling/PlayerScaling.cs)); BoneMod data goes only to BoneMod clients ([page](https://thunderstore.io/c/valheim/p/TOYNBEE/BoneMod/)) |
| Replacing the player model (ValheimVRM, Fenrir Curse, Races of Valheim, GhostWalk) | Yes | Each page says others need the mod ([Fenrir Curse](https://thunderstore.io/c/valheim/p/Nandor/Fenrir_Curse/), [GhostWalk](https://thunderstore.io/c/valheim/p/CranFlakes/GhostWalk/), [ValheimVRM](https://thunderstore.io/c/valheim/p/Mayu/ValheimVRM/)) |

InvisibilityPotion's tier III produces the same visible result as the client-side lie, and its server patch places the same height of 10000 into the header position sent to each other peer. It is the server-side twin of the technique and was built so that the player's own client cannot undo it. The comparison matters for detection. With the potion, the server's copy of the object keeps the real height and carries `IP_Hidden` and `IP_Tier` keys. With the client-side trick, the server's copy already holds the spoofed height and carries `DEV_Ghost` ([HiddenState.cs](https://github.com/saiko-psych/InvisibilityPotion/blob/main/InvisibilityPotion/Net/HiddenState.cs)).

## What does not hide the body for vanilla viewers

Scale does not work. The owner's own finding is that the Player prefab has `m_syncScale=False` and `m_syncInitialScale=False`, so a scale value is not applied to a player's body on other machines (owner's finding in `Transform/transform.md`, cited by the notes). Player_Scaling is consistent with this: it must flip `m_syncInitialScale` to true on the Player prefab on every machine, plus register its own RPCs, which is why it needs installing on all clients and the server. Whether a vanilla viewer ignores a scale value written into a player's data was not tested ([source](https://raw.githubusercontent.com/JereKuusela/valheim-player_scaling/main/PlayerScaling/PlayerScaling.cs)).

Ghost mode alone does not work. Vanilla `Player.SetGhostMode` sets a private field, `m_ghostMode`, with no ZDO key and no RPC, so on another machine `InGhostMode()` returns false for that player. Every public description of vanilla ghost covers enemy AI targeting only ([FreakHosting](https://help.freakhosting.com/games/valheim/using-ghost-mode-and-debugfly), [Steam thread](https://steamcommunity.com/app/892970/discussions/0/3185737486656873051), [Player.cs](https://github.com/VFlov/ValheimMods/blob/main/PrettyPotion/assembly_valheim/Player.cs)). In Server Devcommands ghost mode is only the trigger for the height lie, and the extra `DEV_Ghost` key it writes does nothing for viewers. A cheater's own patch needs no ghost flag, which is an inference.

Releasing ownership of the player object does not hide the body on its own. The owner's finding is that a remote player's visibility is `SetVisible(ZDO.HasOwner())`, which moves the LOD reference point away when the object has no owner. That makes an ownerless player object a plausible cause of an undrawn remote player. The notes contain no test or source describing what happens when a client tries to release the ownership of its own player object, and the instruction for this report records that it does not work. The reason is not documented, so this report states the result without a mechanism (inferred: the server or neighbouring clients would take over an ownerless object).

VisEquipment does not remove the base body. It synchronises hash integers for hands, chest, legs, helmet, shoulder, utility, back, hair and beard, plus skin colour and a body model index that selects one of two models. Items attach by `ObjectDB.GetItemPrefab(hash)`, so any item in the viewer's vanilla database can appear, including non-obtainable monster attack items such as `Serpent_attack` (the owner's IL reading of 1.0.20). No public source lists a vanilla item that covers the whole body, and the handling of an out-of-range model index is unverified. A public item-hiding mod, Transmog, hides one equipped item and needs every connecting player to install it ([Transmog](https://thunderstore.io/c/valheim/p/Alpus/Transmog/)). Immersive First Person's head-hide acts only on the local player's own renderers ([v1.4.0](https://thunderstore.io/c/valheim/p/Gerominoes/ImmersiveFirstPerson/v/1.4.0/)). Neither touches what other viewers see.

## A spawned creature fills the empty space the hidden body leaves

A networked creature is its own object, with its own owner and position, created from a prefab hash that every vanilla client resolves. The height lie changes only the player's own object (`zdo.m_position.y` on the local player), so a creature spawned next to the player is untouched ([GhostFeatures.cs](https://github.com/JereKuusela/valheim-dev/blob/main/ServerDevcommands/Features/GhostFeatures.cs)). Neither piece alone gives a clean disguise. The owner's own test showed that a host-spawned networked Crow placed on the local model is visible to a vanilla second player, but the human body stays visible and the small sitting crow sits inside it (the owner's `transform.md`, cited by the notes). The second piece fixes that: removing the human from the picture leaves the creature as the only thing a vanilla viewer sees. The creature must follow the real position, since the player object carries the spoofed height. A client-owned creature that moves with its owner is a publicly documented pattern: PlayAsMob spawns "standard networked creatures" and ends possession when the client loses network ownership ([PlayAsMob](https://thunderstore.io/c/valheim/p/TenZly/PlayAsMob/v/1.0.1/)). The notes report no test of creature plus height lie together; this combination is inferred.

## What the trick leaks and what it costs the cheater

Shouts and pings carry the real head position as the message position, and receivers use it for in-world text and for a shout pin on the minimap (vanilla `Chat.SendText` in the [Chat.cs decompile](https://github.com/VFlov/ValheimMods/blob/main/PrettyPotion/assembly_valheim/Chat.cs)). Server Devcommands ships a separate setting, `hide_shout_pings`, to force shout pings to the world centre, which suggests its author knows about the leak. The player-list entry stays, so the name still appears in the Tab list; only the position is gated by the public-position flag ([ZNet.cs](https://github.com/VFlov/ValheimMods/blob/main/PrettyPotion/assembly_valheim/ZNet.cs)). A chat text bubble anchors to the object 10 km up. The object keeps moving horizontally at the real x and z, so the body is hidden rather than frozen. A stationary object sends no new revision, so viewers keep the last spoofed state. This is believed harmless but untested.

The costs fall mainly on the cheater. Targeting by other clients is lost: viewers cannot target a body 10 km up, and monsters simulated by other clients likely lose the player (monsters owned by the cheater's client ignore the player under ghost mode). The server sorts outgoing objects by distance to each peer's reference position, so a 10 km-high object is sent last and its updates could be starved under saturated bandwidth (speculative). The patch also strips status-effect start effects on every send. The InvisibilityPotion author lists unresolved side effects at that height: interpolation, ships and carts, voice positioning and ragdolls ([decompile-notes](https://github.com/saiko-psych/InvisibilityPotion/blob/main/docs/decompile-notes.md)). That mod's docs name a further leak, Mumble positional audio ([wiki 05](https://github.com/saiko-psych/InvisibilityPotion/blob/main/docs/wiki/05-Multiplayer-and-Server.md)). Two documentation conflicts do not change the picture. The wiki says a hidden player has no player-list entry, but its code clears only the position. The Player_Scaling tag says client-side while its README says install on the server too.

## Detection and hardening start at the server

Public anti-cheat tooling does not help directly. AzuAntiCheat, koumodgp, Valheim Enforcer, ServerGuard and CharactersVault require the same plugin on the server and every client, and a private server with vanilla viewers cannot use them as built. Their checks also address flags, processes and DLLs rather than a lied height ([Enforcer](https://thunderstore.io/c/valheim/p/MidnightMods/ValheimEnforcer/), [koumodgp](https://thunderstore.io/c/valheim/p/Kou/koumodgp/)). No public tool names "invisible body" or "model swap" detection, and no admin write-up of such a case exists in what the searches reached (Reddit, Discord and Nexus were blocked or not indexed).

The server holds the contradiction the lie creates: each peer sends its true reference position about every 2 seconds, while its player object arrives at a very different height. The signals follow from the code read and are not yet confirmed on a live server.

| Signal | Why it betrays the trick | Confidence |
|---|---|---|
| Player object height far outside the world (about 10000) while the peer's reference position is normal | The height is overwritten only during the send | High (code), unverified live |
| Public-position flag false for a peer that is moving and chatting | The second patch clears it | High (code) |
| `DEV_Ghost` key on the player object (also saved in the world) | Written by the Server Devcommands ghost toggle even when invisibility is off | Medium: the key uses a platform string hash, so compute its numeric value on the same runtime |
| Shout or ping position differs from the player object's position | The message carries the real head position | High (code) |
| Creature object owned by a player peer that tracks that player's position, appears at connect and vanishes at disconnect | The follower-creature pattern | Inference |
| `IP_Hidden` or `IP_Tier` keys | Marks the server-side potion variant, not the client trick | Medium |
| Equipment hashes outside the set of obtainable items | Non-obtainable items such as monster attack items | Heuristic, false positives expected |
| Count of creature objects per peer above normal | A spawned follower | Inference |

Without touching the viewers, the host has these options, in order of cost. First, a server-only BepInEx plugin that logs new objects (prefab, owner, position), ownership changes and one position sample per player per second, plus the peer reference position, for about a week before enabling any block, since blind filtering broke normal play in at least one public case ([VBNetTweaks changelog](https://thunderstore.io/c/valheim/p/VitByr/VBNetTweaks/changelog)). Second, a check in the intake path that compares each player object's height with that peer's reference position and either clamps the value to the peer's real position or kicks, which turns the contradiction into enforcement; this was not tested. Third, block the two routed calls the vanilla client never sends (`SpawnObject` and `TeleportPlayer`), as Valheim Enforcer's `BlockSpawnObjectRPC` does (the owner's earlier IL reading). Fourth, an admin-side view: Server Devcommands' `private_players` shows hidden players' real reference positions to admins, but needs the mod on server and admin client and is off by default ([MinimapPrivatePlayers.cs](https://github.com/JereKuusela/valheim-dev/blob/main/ServerDevcommands/Features/MinimapPrivatePlayers.cs)). Fifth, keep the admin list short, take backups before any blocking, and clean up client-created creatures with a backup restore or an object-remover tool tested on a copy of the world. No documented procedure exists for purging creature objects by owner or prefab, and CheatCleanup clears cheat flags without deleting creatures ([CheatCleanup](https://thunderstore.io/c/valheim/p/Patocino/CheatCleanup/)). Server-only options that exist today are NoCheatItems, which removes items carrying the game's cheat flag ([NoCheatItems](https://thunderstore.io/c/valheim/p/Ageous27/NoCheatItems/)), and a partial Nexus anti-fly/speed mod known only from a search snippet.

## What could not be verified

Nothing here was tested with a second client or on a live server; every behavioural claim comes from reading source. The vanilla code behind the height-lie explanation was read from an older third-party decompile, not the installed 1.0.20 assembly (only identifier names were confirmed in that file). The on-screen behaviour of a remote player at height 10000, the combination with a spawned creature, and the starvation effect are unverified. The commit or release that introduced `ghost_invisibility` was not found, and no issue or release note says it works with vanilla viewers. The option name is spelled `ghost_invisibility` in the README but `ghost_invibisility` in the `dev_config` option list, and which spelling the command accepts was not tested ([Settings.cs](https://github.com/JereKuusela/valheim-dev/blob/main/ServerDevcommands/settings/Settings.cs)). The reason ownership release fails is undocumented. Whether the Player prefab rejects an out-of-range model index is unknown. Whether Valheim Enforcer or koumodgp can enforce in a server-only install is unknown. Several public pages were read through summarising fetch tools, and Nexus pages returned HTTP 403, so statements about those rest on search snippets. Download figures for InvisibilityPotion (166) come from a search summary only.

## Conclusion

The central lesson is that a vanilla client hides a body by lying to the server, not by changing how the body renders. The only hiding route found that works on vanilla viewers is the cheater's own report of where its body is, and the server accepts it because it never compares that report with the second position the same client sends every two seconds. That also locates the defence: the contradiction is visible on the server, so a small server-only plugin can detect it, and the same plugin can clamp it. The trick itself cannot be prevented from the viewers' side.

For the owner's own world, the practical picture follows from the same facts. His own `transform` result (a model made only on his PC is never sent) and the Crow test already show how little can be changed on vanilla viewers by rendering alone. The height lie is the one lever that needs only the cheater's client. A creature spawned next to a hidden body is therefore the most plausible vanilla-visible disguise, and the first thing to check live is whether the player object's height, the peer's reference position and any creature object owned by the same peer agree.
